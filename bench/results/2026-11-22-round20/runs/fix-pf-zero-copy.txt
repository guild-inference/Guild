## change_summary

The fix pass adds two commits on 7650c77, both in src/prefill/prefill.cpp. There is no header, ABI or lock change.

F1 is real but latent, and 6f32e76 fixes it. I confirmed the verifier's chain in the code:
- draft_kv carves B x per_row bytes from m.region, past region_eff and over the lent slots.
- lay_out's second early return ("laid out for this T already") returned before the loop that resets ztail.
- stage_copy skips the pinned path's tail op when zt == bytes.

That early return now sets ztail = 0 for the lent slots [ring - ring_lent, ring). In both modes those are exactly the lent slots. The only effect is extra tail ops on the pinned-arena path; a Stager DMA carries its own zero tail whatever ztail says. Note: bench_runtime's --warmup 1 warms up on the first prompt only. With QWEN_RUNS=1, no two consecutive runs share a lent layout, so no earlier check (the implementer's or the verifier's) ever reached this return. My checks use QWEN_RUNS=2.

Problem 6 and the ZERO_COPY=0 wording, 0714336:
- The Stager's +256 B buffers and per-job tail memset now depend on carve's own condition (zc_layout(T) && !borrowed && next_ == nullptr && stage_lb_ == 0), evaluated in init before the Stager is created. Configs that never get the zero-copy block (HIP, cc >= 7, no --prefill-rows, layer split, borrowed buffers, the user's --prefill 512 server) get the pre-lane Stager back.
- The GUILD_PREFILL_ZERO_COPY=0 comment now says pf-tail-ring's whole path also needs GUILD_PREFILL_TAIL_LEND_STREAMED=0. I kept the two switches independent, each restoring its own change.

F2: the observation is real, the suspected cause is not. I implemented the verifier's fix exactly: the pinned blob's tail as a 256-B DMA from pinned zeros on the copy stream, with GUILD_PREFILL_ZERO_TAIL_DMA=0 as the memset arm (commit 0f22566). It measured no gain in the abP A/B, so I dropped it from the branch with git reset --hard to 0714336; it was my own unpushed commit and its file is kept in fix/split/final.cpp. Why the gain is missing: a 2K chunk streams all 24,576 blobs (55.43 GiB) and is copy-bound with zero-copy on both paths ('wait copy' 1.66 s pinned, 1.21 s unpinned). The page-locked arena delivers about 7.0 GB/s against about 7.45 GB/s through the Stager (estimates: bytes over the GPU timeline). The gather arm's GPU work fits under the same copies, so at 2K on a pinned arena there is nothing to gain. At 4K the chunk is GPU-bound and zero-copy gains 9.4%.

The -22 MiB VRAM: one 160.25 MiB block replaces 34 allocations that the allocator rounds up. No code change is possible short of wasting memory on purpose. Integration should compare texts only at equal 'GPU cache N slots'.

'wait copy' rising at whole 8192-token chunks is not a defect. I measured the optional lever with the same binary (GUILD_PREFILL_RING=64) and did not make it a default.

## switches

- GUILD_PREFILL_ZERO_COPY: default 1. =0 restores the ring slots and group buffers as separate allocations, no Stager zero tail, the group gather, and the gather walk's 192-slot threshold. pf-tail-ring's whole path is GUILD_PREFILL_ZERO_COPY=0 plus GUILD_PREFILL_TAIL_LEND_STREAMED=0; the verifier's F0 run of that pair gave identical hashes. =0 alone keeps follow-up (a)'s lending rule.
- GUILD_PREFILL_TAIL_LEND_STREAMED: default 1. =0 restores pf-tail-ring's rule: every chunk of tail_stream_min() (1,536) tokens or more lends its idle tails, even when it then takes the routed walk.
- GUILD_PREFILL_TAIL_WALK_RING: default unset (78 slots for the in-place walk, 192 for the gather walk). N sets both thresholds to N; 192 restores pf-tail-ring's threshold.
- The fix pass adds no switch. F1 is a bug fix that only adds zero-tail ops on the pinned path. The Stager gating restores the pre-lane Stager exactly where no zero-copy block is carved. GUILD_PREFILL_ZERO_COPY=0 still turns the tail off everywhere, because zc_layout() tests zero_copy_on(). The tried GUILD_PREFILL_ZERO_TAIL_DMA was dropped together with its commit.

## gain_summary

The kept fix-pass changes owe no speed A/B, because they change no device operation in any measured configuration. On the default Stager path, ztail decides nothing, and the gated tail is unchanged wherever the block is carved. On this pack's pinned path, F1's reset adds no tail op, because every slot's first pinned DMA of a request already zeroed its tail (layer 0's blob is 2,329,600 B, layers 46-47's are 3,148,800 B). The single runs on HEAD match the verifier's 'on' arms: TD p2k 8050 vs 8123, p4k 12469 vs 12470, p7600 23220 vs 23170.

So the lane's measured gains stand (the verifier's alternated A/Bs on 7650c77): 2K -13.3%, 3K -14.6%, 4K -13.5%, 6K -9.1%, 7.6K -3.9%, 32K -3.3%, one whole 8192-token chunk -2.7%, 1K unchanged.

On a page-locked arena (abP, M vs Z): 2K -0.9%, 4K -9.4%. The 2K pinned chunk is bound by the expert copies, so zero-copy cannot gain there, and it is not a regression.

The F2 DMA tail gained nothing (2K +0.5%, 4K +0.2% against the memset) and was not kept.

The optional ring lever (GUILD_PREFILL_RING=64 at 8192-token chunks) gives -1.0% on one whole 8192-token chunk for +107 MiB of VRAM. It is not made a default.

## not_taken

- The verifier's F2 fix (the pinned blob's zero tail as a 256-B DMA from pinned zeros on the copy stream, switch GUILD_PREFILL_ZERO_TAIL_DMA). Implemented as 0f22566, measured in abP: no gain at 2K (+0.5% against the memset) or 4K (+0.2%). Dropped from the branch; the file is kept in /home/ubuntu/lanes/r20/pf-zero-copy/fix/split/final.cpp.
- Making GUILD_PREFILL_ZERO_COPY=0 imply GUILD_PREFILL_TAIL_LEND_STREAMED=0. The two switches stay independent and the comment and switch list now say so.
- A larger default ring at 8192-token chunks: measured as an option only (abR), not made a default in a fix pass.
- Resetting ztail after on_chunk instead of at lay_out's early return. The early return covers any writer between two chunks, not only draft_kv.
- A forced debug demonstration of F1 (a fake equal-size first and last layer): not built, to save shared build and GPU time.
- Keeping VRAM use equal to the separate allocations, which would mean wasting allocator rounding on purpose.
