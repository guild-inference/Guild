## switches

- GUILD_HELPER_PIN (lane switch, read once at load, default 1): pins a Drama 3 request's tower and codec threads to ExpertPool::helper_cpus(), the host core's free SMT siblings, CPU 32 on this PC. It pins the request's own thread to the pool's host core only when all three hold: helper_cpus is not empty, every expert is in the RAM copy or the GPU cache, and GUILD_HOST_AFFINITY is not 0. 0 restores the old placement, with all three threads where the OS puts them.
- GUILD_HOST_AFFINITY (existing, default on): for Drama 3 it is now read at load. =0 skips the request-thread pin and keeps the helpers pinned; the load line then says '(GUILD_HOST_AFFINITY=0)'. For the text decode it is unchanged: still read per request, and =0 skips the decode-loop pin.
- No new switch for SpawnAffinity. It only gives fill_many's threads the placement they had before any pin. When the caller is not pinned it does nothing: one mask read, then no change.

## gain_summary

On this PC's default layout (every expert in RAM, 31 workers, CPU 32 free), the final code keeps the lane's gain. GUILD_HELPER_PIN=1 against 0, 6 alternated pairs over both seeds: +2.21% (se 0.26), 48.96 -> 50.04 frames/s, 6 of 6 > 0, the same WAVs. The lane measured +2.61% and the verifier +2.88%.

The blocker is gone. At --resident-budget-gib 6 the pinned arm ran at 7.06 / 6.99 frames/s; now both arms run 14.8-17.7 (on arm 17.19 / 17.23 / 17.66).

On the emulated no-SMT and 16-worker layouts, both arms now place every thread the same way, where the OS puts them.

The pre-existing text decode problem (6) was real and is fixed. Qwen at --resident-budget-gib 24 ran at 7.11 tok/s with the pinned decode against 13.36 unpinned on a61963a's binary. With SpawnAffinity the pinned decode runs at 13.66 against 13.40 unpinned (one pair).

## not_taken

- place_thread (pthread_setaffinity_np on each new thread's handle): racy. When the thread has already exited, the call sets the creator's own mask, so the request thread lost its pin. Replaced by SpawnAffinity; the commits were rewritten.
- Keeping Drama 3's request pin when experts are read from the files: with SpawnAffinity it still cost 9.83% (4 pairs, 0 of 4 > 0), so it now waits for every expert in RAM.
- A new switch for the fetch-thread placement: not added. It only restores the placement these threads had before any pin.
- Sampling the old binary's Qwen fetch threads: its copy's comm name is truncated to 'guild-generate-', so --find missed it. The speeds carry the result.

In Drama 3's pinned low-RAM runs (b2), the request thread sat on the wide mask for about 2/3 of the 50 ms polls: starting 7 threads a layer takes most of a layer's time there. A persistent fetch-thread pool would avoid this; not tried.
- Windows: SpawnAffinity does nothing there, and helper_cpus is empty there, so Drama 3 no longer pins its request thread on Windows. Whether Windows threads inherit a CPU Set selection was not measured (no Windows machine here).
