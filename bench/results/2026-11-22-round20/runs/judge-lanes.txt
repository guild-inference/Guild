## pf-tail-ring
- title: Prompt chunks below 8,192 tokens: re-carve the prompt region for the chunk's own T, lend its idle tail and R's idle rows to the expert ring, and take the streamed walk from ~2K tokens
- models: ["Qwen3.8-Flash-Next (prompts of ~2K-8K new tokens, and the last chunk of longer prompts)"]
- goal: Cut the ~3.1 s of 'wait copy' that 1-4K prompts spend today (below 4,096 tokens the routed 8-slot walk issues copies only after each layer's routing sync, so the copy engine idles through every dense half) by giving chunks shorter than T_max = 8192 a ~250-360-slot streamed ring carved from VRAM the chunk leaves unused, without shrinking the 8192-token chunk long prompts use.
- expected_gain: Measured with the env equivalent (a 256-slot ring carved at init, one run each, hashes identical): 4,008-token prompt 16.10 -> 14.74 s (-8.5%), 2,008 -> 9.90 s (-5.1%). The tail gives ~254 slots at 4K and ~359 at 2K without the env runs' smaller auto chunk (8192 kept). 1K unchanged (stays routed); 5-6K single chunks likely -5 to -8%; 7.6K ~-1% (~31 more slots); 32K only its last chunk (~-0.3 s of ~106 s). Stretch pf-dense-xq: -0.07 s at 4K, -0.55 s at 32K.
- stop_rule: Stop and report (WIP commits kept, the NOTES.md table) if the 4K prompt gains less than 3% over the 2 alternated pairs, or if any hash differs and the cause is not found within ~1 hour. Steps 7 and 8 only after 1-6 are committed and measured; drop either if it gains nothing.

## helper-threads (batch3.json)
- goal: Keep the busy helper threads that run beside a model's decode (Drama 3's two Beside threads first) off the physical cores of the CPU expert pool's workers, so the pool's rows stop losing to a busy SMT sibling. Output bits identical: only which CPU a thread runs on changes.
- evidence:
  - cpu-rows/NOTES.md, ps -L samples during a default Drama 3 decode (48.52 frames/s, 6e04c9b1): the 31 pool workers on CPUs 1-31 (one a physical core), the generation thread on core 0 (CPU 0 / sibling 32, ~91%), and two unpinned busy threads, ~40% CPU on CPU 36 and ~15-19% on CPU 35, the SMT siblings of pool workers 4 and 3, in all 8 samples.
  - With GUILD_POOL_WORKERS=30 (core 31 left free) the kq rows (GUILD_KQ_ROWS512) took 0.17-0.31 ms a frame off the pool walls, against 0.01-0.02 ms with 31 workers; 13 of the 40 layers (2, 3, 15, 18, ..., 33, 36-39) got 5-9 us slower with the kq rows when a busy sibling shared their core. 30 workers were slower overall than 31 (pool walls 4.82-4.94 against 4.71-4.74 ms a frame), so freeing a core by dropping a worker is not the fix.
  - The two threads are very likely src/runtime/drama3.cpp's two Beside threads (class Beside, std::thread t_, cudaSetDevice then a job loop): `beside` runs the tower's step_finish (a frame's codes 2..9) beside the backbone's next row, `codec_side` runs the codec's chunks. Neither is pinned. The generation thread is pinned to the pool's host core (src/runtime/session.cpp / src/core/cpu_moe.cpp pin helpers; the pool's topology code is include/guild/kernels/cpu/pool.hpp detect_cpu_topology / physical_cores / PoolAffinity). Confirm by thread name and TID before acting.
- expected_gain: Drama 3 +0.8-1.5% frames/s (0.17-0.31 ms of ~20.6 ms a frame), if the Beside threads cost the pool what the 30-worker hold suggests and the host core's sibling absorbs them without slowing the generation thread. Unknown for the other models.
- stop_rule: If every placement in step 1 gives < +0.3% over 2 pairs on both seeds, stop: report the measured no-go (with the thread identification and the numbers) and change no code beyond, at most, the thread names. Budget about 3 hours.
