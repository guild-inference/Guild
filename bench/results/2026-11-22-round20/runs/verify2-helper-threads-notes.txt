## 12. Code review of 4f3ce6d..d9a3dda, the fix commits most closely
SpawnAffinity (5114561):
- Correct mechanism: a Linux thread's mask is copied at clone(), so a thread started while its creator runs on the
  recorded mask keeps that mask whatever the creator does next; the creator's own mask comes back in the destructor,
  before its own share of the copies (work()) and the joins.  The fixer's reason to drop place_thread is right (glibc's
  pthread_setaffinity_np on an exited thread's handle passes TID 0, the caller).
- Per-thread only: get/set act on pthread_self(); fetch_affinity_ is written in open()/open_gpack() (after close())
  and only read afterwards, so concurrent fill_many calls (none exist today: one drive thread a model) cannot race.
- Recorded where intended: open()/open_gpack() run on the loading thread (model.cpp ~792-814) before any temporary pin
  of that thread (the verifier's HostAllocAffinity at ~1275, the prefill Stager's at its init); the ExpertPool built
  before them pins only its workers.  Checked in the engine: with the decode unpinned (GUILD_HOST_AFFINITY=0)
  SpawnAffinity is a no-op (equal masks) and the speeds equal round 19's unpinned ones.
- Failure paths: a refused widening (EINVAL: no CPU of the recorded mask left in a shrunken cpuset or online) leaves
  own_ invalid, nothing changed, the threads inherit the caller's mask (the old behaviour); a partly valid mask is
  intersected by the kernel; a refused restore prints "host affinity restoration failed" once and leaves the caller on
  the wide mask until the request's own restore.  An exception from th.emplace_back unwinds through the destructor
  (mask restored), then reaches `th` with joinable threads -> std::terminate: pre-existing, unchanged.
- Cost: one sched_getaffinity + compare per call with nt > 1; two sets more when the caller is pinned.  Not measurable:
  int pinned vs unpinned decode time -3.1, -3.5, +2.0% (Q4).
- Behaviour change to note (nit): the threads take the LOAD-time mask, not the caller's, so a restriction applied
  after load by someone else (taskset -a -p on the running process, an embedding app narrowing its request thread to
  a node) no longer reaches fill_many's threads; cpusets still do (kernel-enforced).  A cheap guard if wanted: widen
  only when the caller's mask is one CPU (Guild's host-core pin).
- The Windows direct path (open_direct, the only one that sets direct_) starts its threads without SpawnAffinity; it is
  a no-op there anyway (Windows thread selections are per thread; not measured here).

The gate (0eb63a0):
- experts_in_ram = complement_ready && resident_experts() + slots >= total.  Explicit --expert-cache N: the cache is
  filled before pin_cache_complement, whose plan excludes exactly the cached pairs (lend_from_slot -1: no overlap), so
  the sum means "every expert on the GPU or in RAM".  Auto cache: slots is 0 at this point (filled later), so it needs
  every expert in RAM: conservative.  Partial copy (budget, or the source clamping to free memory): false.  Zero-copy
  mmap (GUILD_EXPERT_MMAP=1) or no copy: complement_ready false -> no pin (conservative).  Later changes: none (the
  complement is set once, cleared only by close(); the GPU cache is filled only at load; override_ exchanges do not
  remove complement entries).  With the gate true, prefetch() returns before fill_many for every CPU expert.
- GUILD_HOST_AFFINITY parsed as session.cpp/batch.cpp do (unset or atoi != 0), read at load for Drama 3 only.
- Load lines checked in D1/D2: the three wordings match the three gate outcomes.  Nit: on Windows the third wording
  gives "no free SMT sibling ..., or not one worker a core" where the reason is that host_siblings is not filled there.
- GUILD_HELPER_PIN=0: helper_cpus empty -> neither pin (D1/D3 off arms: all three threads 0-63, every run).
